# 数据与配置的保险

用户的配置与交易库要经得住三件事:写到一半进程没了、文件自己坏了、升级之后想回头。这份文档写四样:配置文件、交易库、发单之前的留痕,
以及出事时桌面端怎么接。

## 配置文件(`settings.json`)

- **原子写**(`config.ts` 的 `writeFileAtomic`):先写同目录的临时文件、`fsync`、再 `rename`,中途打断时留下的要么是旧文件要么是新文件。
  例外:`rename` 失败时(Windows 上常见于杀毒或同步软件占着文件)退回直接覆盖写,这一次不是原子的;`desktop/config-guard.js` 与
  `desktop/accounts-setup.js` 的写入同样如此。
- **备份**:每次从界面改设置之前,把改之前那一份存成 `settings.json.bak`(它刚被读进来过,是能用的)。
- **读不进来**抛 `ConfigLoadError`,分 `missing` / `syntax` / `invalid`。引擎只打一行 `[fatal:config:<kind>] <原因>`,退出码 `EXIT_CONFIG`(78);
  `invalid` 的原因就是校验那一句原话。
- 主进程认出 78 就不再自动重启,弹对话框:「恢复上一份可用的配置」(有备份、且和现在这份不一样时才有)、「打开配置文件所在位置」
  (点完对话框会再出来)、「我改好了,重试」、「退出」。主进程只认得出 JSON 语法,字段对不对由引擎启动时校验,还不过就再弹一次。
- **不自动恢复备份**:备份比现状旧,用户刚关掉「允许自动执行」时写盘出事,自动恢复会把它悄悄打开。
  恢复只在用户点了按钮之后做,恢复出来的配置里**三个执行闸门一律关闭**;坏的那一份改名成 `settings.json.broken-<时间>` 留在旁边。

## 交易库(`trades.db`)

全在 `engine-ts/src/storeSafety.ts`。`TradeStore` 构造时带 `{ safety: true }` 才走这一套,真应用的引擎装配与启动探测都带着;
测试与黄金基线开的库不带,行为不变。

**结构版本**:`PRAGMA user_version`,现在是 `SCHEMA_VERSION = 1`,0 表示还没有版本号的库,当作最旧。

| 库的版本 | 做什么 |
|---|---|
| 比软件新 | 拒绝打开(`StoreOpenError`,`newer`),提示升级软件:旧软件不认识新结构,硬开可能写坏 |
| 比软件旧 | 先留一份 `upgrade` 备份,再迁移,最后盖上新版本号 |
| 一样 | 照常 |

改表结构(加列以外的)时 `SCHEMA_VERSION` 加一,在 `store.ts` 的 `migrate` 里写迁移。加列用 `table_info` 探测 + `ALTER TABLE ADD COLUMN`,
不动版本号:旧软件打开多了一列的库没有问题。整表重建放在 `db.transaction()` 里,出错整段回滚。

**备份**:`VACUUM INTO` 一条语句出一份一致的快照(WAL 里还没并回去的也在),不用停库。放在库旁边的 `backups/`,
文件名 `trades-<年月日>-<时分秒>-<原因>.db`,时间用 UTC,同一秒出两份时加 `-N` 后缀。

| 原因 | 什么时候 | 保留几份 |
|---|---|---|
| `daily` | 打开库时,上一份 daily 是 20 小时之前的(新建的库、同一次打开已经出了 upgrade 备份时不出) | 7 |
| `upgrade` | 库的版本比软件旧,迁移之前 | 3 |
| `manual` | 用户点「立即备份」;从备份恢复之前自动留的那一份 | 5 |

- 备份失败不挡开库(磁盘满了不该连带让持仓追踪停掉),只往 stderr 记一句。完整性检查没过的库不备份。
- 备份和库在同一块盘上,防得住误操作、软件缺陷、升级出错,防不了硬盘损坏;界面与用户手册都写明要另拷一份。
- `data.backups`(库与备份目录的位置、结构版本、备份清单)与 `data.backup`(现在出一份 `manual`)在本地道,都不是敏感方法。

**打不开的时候**:`PRAGMA quick_check` 每个进程对每个库只做一次。引擎启动时先把库开一遍:库是懒建的,不先开的话引擎会"正常启动"、
每个请求都失败、被心跳当成不回话反复重启。打不开就当场退出,退出码 `EXIT_STORE`(74),stderr 末两行是
`[fatal:store:path] <库路径>` 与 `[fatal:store:<kind>] <原因>`。

| kind | 情况 | 对话框上能做什么 |
|---|---|---|
| `corrupt` | 不是数据库文件、完整性检查没过 | 用最近的备份恢复 / 打开所在位置 / 重试 / 退出 |
| `locked` | 被另一个进程占着(多半是另一个实例没退干净) | 打开所在位置 / 重试 / 退出 |
| `unwritable` | 目录只读、磁盘满 | 同上 |
| `newer` | 见上 | 同上 |

**恢复**:入口是「设置 → 数据与备份」里某一份的「恢复到这一份…」,以及库打不开时对话框里的「用最近的备份恢复」。都在主进程做
(`desktop/store-guard.js`),换库文件时引擎必须停着。

- 界面递过来的只是文件名,只认引擎起的那种名字,只从 `backups/` 里取;先核对备份开头 16 个字节是 SQLite 的文件头。
- 现在这份库不删:改名成 `trades.db.before-restore-<时间>`(打不开的是 `.corrupt-<时间>`),`-wal` / `-shm` 一起挪走,否则新库会被旧 WAL 回放坏。
- 先拷到旁边的临时文件再 `rename`,拷到一半断电也不会出现半个文件。
- 从界面恢复时,停引擎之前先让它再出一份 `manual` 备份。

## 发单之前先留痕(`submit_intent`)

记录在发单之前建立,第一条状态回报却要等券商回话才写入。引擎进程恰好在这中间结束时,单子可能已经到了券商,库里这条记录却一条状态都没有,
对账与重复单检查都认不出它,原样再发一次就是双倍仓位。所以四处发单之前都先追加一条 `submit_intent` 事件(`store.markSubmitIntent`):
立即单、触发的条件单、持仓追踪的自动平仓、托管单。

它是新的事件种类,`foldEvents` 不认识的种类直接跳过,折出来的记录文档一字不变;对账(`listWorkingRecords`)与重复单检查(`recentOrders`)
的查询认它。重启之后对账怎么处理这种记录,见 [执行对账](reconcile.md)。

## 桌面端配套

- **停引擎先排空**(`rpc-client.js` 的 `stop`):关 stdin → 引擎答完在途请求自己退出 → 3 秒后还没退才 SIGTERM → 再过一段宽限期 SIGKILL。
  心跳判定已死的引擎不排空。
- **退出应用等引擎停稳**(`before-quit` 里先拦下,停稳了再 `app.quit()`),否则卡住的引擎会变成孤儿进程。
- **自动重启的退避**:引擎意外退出后按 3 秒起、翻倍、最长 60 秒的间隔重启;连续运行超过 5 分钟后退避清零。退避期间主进程 `holdUntil`,
  界面的轮询不会顺手把它拉起来;配置坏了、库打不开时无限期暂停,并带一句原因。
- **发单类调用超时报「结果未知」**,引擎迟到的回执到了再补一条通知,见 [引擎 RPC](engine-rpc.md)。
- **排队的条件单多一个驱动**:连着券商且有排队的单时(富途下一律),主进程跟着心跳也调 `pending.poll`,界面崩溃、重载期间照样有人问。

## 还没做的

- 备份只在本机,异地备份(另一块盘、云盘)要用户自己拷。
- 没有导入:`data.export` 出的 JSON 只有交易记录与审计日志,给人看、给别的工具读;完整的备份是 `.db` 文件。
- `synchronous` 沿用 better-sqlite3 在 WAL 下的默认(NORMAL):进程被杀不丢数据,整机断电可能丢最后几笔提交,不会坏库。
- 以上只有离线测试。恢复那条路要在真机上走一遍:有追踪、有托管单时恢复到昨天的备份,看对账怎么认领。
