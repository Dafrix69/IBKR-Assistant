# 数据与配置的保险:写不坏、坏了有路、丢了找得回

2026-09-28 加的。卖出去的软件,用户的配置与交易库要经得住三件事:写到一半进程没了、文件自己坏了、
升级之后想回头。在这之前三件都没有着落——配置是直接覆盖写的,坏了引擎就无限重启;交易库没有版本号、
没有备份,打不开时每个操作回一句英文的 `SqliteError`。

这份文档讲四样:配置文件、交易库、发单之前的那条痕、以及这几样出事时桌面端怎么接。

## 配置文件(`settings.json`)

| 以前 | 现在 |
|---|---|
| `fs.writeFileSync` 直接覆盖 | 先写同目录的临时文件、`fsync`、再 `rename`(`config.ts` 的 `writeFileAtomic`)。任何一步被打断,留下的要么是旧文件要么是新文件 |
| 没有备份 | 每次从界面改设置之前,把**改之前**那一份存成 `settings.json.bak`。它刚被读进来过,是能用的 |
| 读不进来抛一个普通 `Error`,`cli.ts` 打十行调用栈、退出码 1 | 抛 `ConfigLoadError`,分 `missing` / `syntax` / `invalid`。引擎的 rpc 入口只打一行 `[fatal:config:<kind>] <人话>`,退出码 `EXIT_CONFIG`(78) |
| 主进程按"引擎崩了"自动重启,退避到 60 秒一次,永远不停 | 主进程认出 78:不再重启,弹对话框(见下) |

`invalid` 的话就是校验那一句原话,不加前缀——那些话和 Python 版逐字节一致,黄金基线在比。

**为什么不自动恢复备份。** 备份比现状旧。用户刚把「允许自动执行」关掉,写盘时出了事,自动恢复会把它悄悄打开。
所以恢复只在用户点了按钮之后做,而且恢复出来的配置里**三个执行闸门一律是关的**(`desktop/config-guard.js`):
宁可让人再去打开一次。坏的那一份不删,改名成 `settings.json.broken-<时间>` 留在旁边——里面可能有他刚手改进去的账户。

对话框四个按钮:「恢复上一份可用的配置」(有备份、且和现在这份不一样时才有)、「打开配置文件所在位置」
(点完对话框会再出来,改好了点重试)、「我改好了,重试」、「退出」。

主进程只认得出 JSON 语法;字段对不对是引擎的事。恢复之后引擎启动时照常校验,还不过就再弹一次。

## 交易库(`trades.db`)

全在 `engine-ts/src/storeSafety.ts`,`TradeStore` 构造时带 `{ safety: true }` 才走这一套。
**测试与黄金基线开的库不走**:不建备份目录、不盖版本号,老行为一字不变。真应用的两处(`rpc/server.ts` 的
引擎装配、启动时的探测)带着它。

### 结构版本号

`PRAGMA user_version`,现在是 `SCHEMA_VERSION = 1`。版本号 0 = 还没有版本号那时候的库,当作最旧。

| 库的版本 | 做什么 |
|---|---|
| 比软件新 | **拒绝打开**(`StoreOpenError`,kind `newer`):老软件不认识新结构,硬开可能写坏。提示升级 |
| 比软件旧 | 先备份(原因 `upgrade`),再迁移,最后盖上新版本号 |
| 一样 | 照常;每天第一次打开留一份 `daily` 备份 |

以后改表结构(加列以外的)就把 `SCHEMA_VERSION` 加一,并在 `store.ts` 的 `migrate` 里写迁移。
加列照旧用 `table_info` 探测 + `ALTER TABLE ADD COLUMN`,不用动版本号:老软件打开多了一列的库没有问题。

`position_tracks` 的整表重建原来是裸的 `BEGIN … COMMIT`,半路出错事务悬着;现在放进 `db.transaction()`,出错整段回滚。

### 备份

`VACUUM INTO`:一条语句出一份一致的快照,WAL 里还没并回去的内容也在里面,不用停库。
放在库旁边的 `backups/`,文件名 `trades-<年月日>-<时分秒>-<原因>.db`,时间用 UTC(换个时区打开,先后次序不变)。

| 原因 | 什么时候 | 留几份 |
|---|---|---|
| `daily` | 打开库时,上一份 daily 是 20 小时之前的 | 7 |
| `upgrade` | 库的版本比软件旧,迁移之前 | 3 |
| `manual` | 用户点「立即备份」;从备份恢复之前自动留的那一份 | 5 |

**备份失败不挡开库。** 磁盘满了不该连带着让持仓追踪停掉;它只往 stderr 记一句。
完整性检查没过的库不去备份——备份一个坏库没有意义,还会把好的那几份挤掉。

备份和库在同一块盘上:它防的是误操作、软件缺陷、升级出错,防不了硬盘坏掉。界面上和用户手册里都写明了要另拷一份。

### 打不开的时候

`PRAGMA quick_check` 每个进程对每个库只做一次(引擎每改一次设置就重建一次 store)。

| kind | 什么情况 | 对话框上能做什么 |
|---|---|---|
| `corrupt` | 不是数据库文件、完整性检查没过 | 用最近的备份恢复 / 打开所在位置 / 重试 / 退出 |
| `locked` | 被另一个进程占着(多半是另一个实例没退干净) | 打开所在位置 / 重试 / 退出 |
| `unwritable` | 目录只读、磁盘满 | 同上 |
| `newer` | 见上 | 同上 |

引擎启动时先把库开一遍(`rpc/server.ts` 的 `main()`):库是懒建的,不先开,引擎会"正常启动",然后每个请求都失败,
主进程的心跳把它当成"不回话",每三分钟强制重启一次。打不开就当场退出,退出码 `EXIT_STORE`(74),
stderr 末两行是 `[fatal:store:path] <库路径>` 与 `[fatal:store:<kind>] <人话>`。

只有 `corrupt` 才给「恢复」:被占着、写不进去、版本太新,换一份库解决不了。

### 恢复

两个入口:「设置 → 数据与备份」里点某一份的「恢复到这一份…」;库打不开时对话框里的「用最近的备份恢复」。
都在主进程做(`desktop/store-guard.js`)——换库文件时引擎必须是停着的。

- 界面递过来的只是一个**文件名**,不是路径;只认引擎起的那种名字,只从 `backups/` 里取。
- 先核对备份开头 16 个字节是 SQLite 的文件头。
- 现在这份库**不删**:改名成 `trades.db.before-restore-<时间>`(打不开的是 `.corrupt-<时间>`),`-wal` / `-shm` 跟着一起挪走。
  留着旧的 WAL,新库会被它"回放"成一锅粥。
- 先拷到旁边的临时文件再 `rename`:拷到一半断电,库的位置上不会出现半个文件。
- 从界面恢复时,停引擎之前先让它再出一份 `manual` 备份。

## 发单之前先留痕(`submit_intent`)

记录是在发单之前建的,第一条状态回报却要等 `await router.place(...)` 回来之后才落。桌面端重启引擎、退出应用、
心跳判死,都会在任意时刻结束引擎进程——正好落在这中间时,单已经到了券商,库里这条记录一条状态都没有。
对账(`listWorkingRecords`)与重复单防抖(`recentOrders`)只认"有过状态回报"的记录:重启后没人认领这张单,
界面上也看不见它,照原样再发一次不会被提醒——双倍仓位。

现在四处发单之前各追加一条事件(`store.markSubmitIntent`):立即单、触发的条件单、追踪器的自动平仓、托管单。

**为什么是一个新的事件 kind,而不是一条 `Submitting` 状态。** `foldEvents` 不认识的 kind 直接跳过,
折出来的记录文档一字不变:状态时间线里不多一行,黄金基线不用动,界面不用多认一个状态词。
要改的只有那两条 SQL 的 `EXISTS` 子句。

重启之后对账怎么处理这种记录:

| 券商那边 | 结果 |
|---|---|
| 单挂着(orderRef = 记录 id) | 认领回来,之后的回报落到这条记录上 |
| 已经成交 | 按成交表补录,落 `filled` |
| 都没有 | 过了宽限期标 `NotAtBroker`,提醒语写明"发单途中软件中断了,它多半没有发出去",不落终态 |

## 桌面端配套

- **停引擎先排空**(`rpc-client.js` 的 `stop`):关 stdin → 引擎答完在途请求自己退出 → `drainMs`(3 秒)后还没退才 SIGTERM
  → 再过 `killGraceMs` SIGKILL。心跳判死的引擎不排空(`drainMs: 0`):它已经不回话了。
- **退出应用等引擎停稳**(`before-quit` 里 `preventDefault`,停稳了再 `app.quit()`)。不等的话主进程先走,
  SIGTERM / SIGKILL 的定时器跟着没了,卡住的引擎会变成孤儿。
- **发单类调用超时报「结果未知」**,引擎迟到的回执到了再补一条通知(`late-reply`)。见 [引擎 RPC](engine-rpc.md)。
- **重启退避拦得住轮询**:引擎退出后主进程 `holdUntil(到点)`,这之前界面的轮询不会顺手把它拉起来。
  配置坏了、库打不开时是无限期地 hold,并带一句原因。
- **排队的条件单多一个驱动**:主进程跟着心跳也调 `pending.poll`。界面崩溃、重载期间条件单照样有人问。

## 还没做的

- 备份只在本机。异地备份(另一块盘、云盘)要用户自己拷。
- 没有"导入":`data.export` 出的 JSON 只有交易记录与审计日志,是给人看、给别的工具读的,不是备份。完整的备份是 `.db` 文件。
- `synchronous` 沿用 better-sqlite3 在 WAL 下的默认(NORMAL):进程被杀不丢数据,整机断电可能丢最后几笔提交,不会坏库。
- 以上都只有离线测试。恢复那条路要在真机上走一遍:有追踪、有托管单时恢复到昨天的备份,看对账怎么认领。
