# 执行对账:重启 / 重连之后,券商那边的真相怎么搬回库里

`orderIndex`(券商的 orderId / permId → 记录 id)只在内存里。引擎实例一重建——重启应用、在「接入」页重连
券商、改配置——它就是空的。券商随后推来的状态与成交,`recordFor()` 认不出属于哪条记录,只能进
`unmatchedEvents` 那个 200 条的缓冲,而缓冲**只有下一次下单才会重放**。

托管单有 `adoptHosted`(按 `trk:<追踪>:<单型>` 认领)、追价平仓单有 `adoptCloseChase`(按记录 id 认领),
**普通单与条件单两样都没有**:`adoptHosted` 见 orderRef 不是 `trk:` 前缀就直接跳过。结果是那条记录永远停在
`Submitted`,库里没有终态,界面上一直显示「进行中」——而券商那边它可能早就成交了、或者早就没了。
`adoptHosted` 也只认回托管单本身(`hostedIndex`),**不认回托管单那条记录**:重启后它的成交、佣金落不到记录上。

`engine.reconcileOrders()` 补的就是这一段。

## 三条路,都只认证据

券商侧的未成交单用的还是现成那条路:`listOpenOrdersDetailed()` → `listHostedOpen("")` →
`session.openTradesDetailed()` → `api.getAllOpenOrders()`(跨 client,拿得到别人挂的单,所以一律按 orderRef 认)。
本地的在途单由 `store.listWorkingRecords()` 给出:回报过状态、还没有终态的记录(`ValidatedOnly` 不算——它从没提交过)。

| 情形 | 做什么 |
|---|---|
| ① 券商侧还挂着:普通单 orderRef = 记录 id;托管单 orderRef = 记录的 signature(`trk:…`) | orderId 与 permId 都指回记录,追加一条状态事件(`source: "reconcile"`),然后重放缓冲里的事件。**之后这张单的回报就认得出记录了** |
| ② 券商侧没有,但 `broker_fills` 里查得到成交,且数量填满 | 补录成交事件(按 exec_id 去重),落 `filled` 终态,提醒一次 |
| ③ 其余去向不明的——**而且这一轮刚问过券商当天的成交** | 只追加一条 `NotAtBroker` 状态事件 + 提醒一次,**不落终态** |

**托管单的记录怎么认**(2026-09-27 审计 H1):托管单的 orderRef 是 `trk:<追踪>:<单型>`,也就是它那条记录的
`signature`,不是记录 id。以前对账见 `trk:` 一律跳过,可托管单的记录照样在在途记录里——每张活着的托管止损都被报成
「去向不明」,每次改价追加的 `Adjusted` 又把状态刷掉,于是一分钟报一次。现在按 signature 认;同一追踪同一单型可能留下
多条记录(被拒后重挂、券商不认后重挂),再按记录状态里留的 `order_id` / `perm_id` 分,认走的单不给第二条记录。
成交表里的成交也一样:按 signature 取、再按单号筛,同一追踪更早那几张单的成交不算到它头上。

**③ 之前先问券商**(审计 H2):`broker_fills` 只有交易分析那一页同步时才写。应用关着时成交了的单,重启后以前会被报成
"券商侧已经没有这张单,也没查到它的成交"——照这句话重下一张就是双倍仓位。现在走到 ③ 之前,router 有 `executions()`
(IBKR = reqExecutions)就先要一遍当天的成交、存进 `broker_fills`、再按 ② 结一次;**问失败、超时、或者被节流时,这一轮
不下 ③ 的结论**,留给下一轮——晚几分钟说,好过说错。router 给不了成交(别家券商、测试替身)才照旧按本地成交表下结论。
券商只回**当天**的成交(TWS 的交易日志设置可以放宽到几天),更早成交的仍会落进 ③,提醒语里写明了要去 TWS 核对。
缺口:router 没有 `reqCompletedOrders`,分不出"撤了"与"更早成交了",两者都只能是 ③。

**③ 为什么不落终态**:终态在 append-only 的库里是不可逆的。券商侧查不到、成交表里也没有,只能说明
"这里看不见它",不能证明它被撤了——可能是 TWS 换了会话、可能是当天的成交还没同步下来。把一张其实还活着的单
标成作废,比让用户多看一眼「去向不明」危险得多。所以这一档只陈述事实,由用户决定。

重启后没人盯的**条件单**(AUTO_MID 定价那一类,只在引擎内存里排队,从没发给券商)也走 ③:
提醒语换成"软件重启后条件单不再被盯,要继续请重新提交",但同样不替用户作废它。

**② 为什么只认 BAG 行**:组合单 IBKR 会回 1 条 BAG 行 + 每条腿各一行。腿加起来是份数的好几倍,
拿它判"填满了没有",一张只成交了一半的蝶会被标成已成交——与 `foldEvents` 折均价时只认 BAG 行同一个道理。

## 什么时候跑

- **接上新会话就安排下一轮**:`wireSession()` 里调 `reconcileSoon()`。断线期间的成交、撤单只能靠这一轮搬回来。
- **之后 60 秒一轮**,挂在盯盘节拍器里(与盯盘共用 `trackerLock`:它会改 `orderIndex` 与终态,不能和一轮盯盘并发)。
  没有任何追踪时盯盘会提前返回,所以对账写在那个提前返回**之前**——没有持仓要盯,不等于没有在途单要对。
- 对账自己吞异常并留痕(`reconcile_failed`),**绝不带倒盯盘**:盯盘停一秒是止损晚一秒。
- **向券商要的每样东西最多等 10 秒**(审计 M2)。IBApiNext 的 `getAllOpenOrders` / `getExecutionDetails` 自己没有超时:
  会话在请求途中被断开(「断开」按钮、换连接),结束信号永远不来。对账又是在 `trackerLock` 里跑的,而那把锁跨引擎实例
  共用——以前这一下能把盯盘、「立即平仓」、熔断按钮一起挂死到进程退出。现在超时就作罢这一轮(留痕 `reconcile_failed` /
  `reconcile_fills_failed`),下一轮再来;底下那个请求撤不回来,它迟到的结果直接丢掉。
- **当天成交最多 5 分钟问一次**:reqExecutions 回的是当天全部成交,不便宜。接上新会话(`reconcileSoon()`)时不受这条限制,
  断线那段时间正是成交最可能漏掉的时候;待定的单全都已经标过 `NotAtBroker` 时也不去问(标记本来就只落一次)。

## 刻意放过的

| 放过谁 | 为什么 |
|---|---|
| 最后一次动静不到 2 分钟的单 | 券商侧的未成交单列表有滞后,新单会被当成失联,冒出一条假的「去向不明」。"最后一次动静"取记录创建与最后一条状态回报里晚的那个(审计 M4):等了三个小时才触发的条件单,一发出去就是"刚发的",只按创建时刻算会把它当成失联。晚于这一轮 now 的状态回报不作数(那是等券商回话时落的,下一行兜住) |
| 本进程还在盯的条件单 | 它本来就没发给券商,`pendingTriggers` 里有就不算失联。队列在**等券商回话之前**先记一份:等的那几百毫秒里条件单可能触发、发出、从队列摘掉,而券商这次给的列表是发单之前的 |
| 7 天前的记录 | 再往前翻已经是历史,当天的成交早同步完了,只会让每一轮对账更慢 |
| 托管单本身(`hostedIndex`、改单缓存) | 归 `adoptHosted`,它还带同 ref 重复单的去重(留单号最新的,其余撤掉)。对账只认回托管单的**记录** |
| 富途 | router 没有 `listOpenOrdersDetailed` 就空转(OpenD 走的是拉取式 `syncBrokerOrders`) |

## 界面

`NotAtBroker` 在记录页与看板上是**黄色的「去向不明」**,不是蓝色的「进行中」——继续显示成在途,
就是让人等一个不会来的回报。记录页的状态筛选也多了同名的一档,「进行中」里不再混进它们。

## 发到一半被杀的单(2026-09-28)

在途记录以前只认"有过状态回报"的,而第一条状态回报要等 `router.place()` 回来才落。引擎进程在发单途中被结束时,
单可能已经到了券商,库里这条记录却一条状态都没有——对账看不见它。现在发单之前先留一条痕(`submit_intent`),
`listWorkingRecords` 认它:

- 券商那边挂着 → 情形 ①,认领回来;
- 已经成交 → 情形 ②;
- 都没有 → 情形 ③,提醒语换成"发单途中软件中断了…它多半没有发出去"。这种记录的 `lastStatus` 是空串。

为什么是新的事件 kind 而不是一条状态、桌面端为什么会在发单途中结束引擎,见 [数据与配置的保险](durability.md)。
`tests/submit-intent.spec.ts` 钉着。
