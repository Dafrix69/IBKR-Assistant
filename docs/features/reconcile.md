# 执行对账

`orderIndex`(券商的 orderId / permId → 记录 id)只在内存里,引擎一重建(重启应用、重连券商、改配置)就是空的。券商随后推来的状态与成交认不出属于哪条记录,
那条记录会一直停在「进行中」,而券商那边它可能早就成交了、或者早就没了。执行对账把券商侧的真相搬回库里:`engine/reconcile.ts` 的 `Reconciler`
(`engine.reconcileOrders()` 转给它)。托管单本身由 `adoptHosted` 认领、追价平仓单由 `adoptCloseChase` 认领,见 [持仓追踪](tracker.md);对账管的是**记录**。

## 三种情形,只认证据

券商侧的未成交单:`listOpenOrdersDetailed()`(跨 client,拿得到别处挂的单,所以一律按 orderRef 认)。本地的在途单:`store.listWorkingRecords()`
给出有过状态回报或发单留痕(`submit_intent`)、还没有终态的记录(`ValidatedOnly` 从没提交过,不算),最多 200 条。

| 情形 | 做什么 |
|---|---|
| ① 券商侧还挂着 | orderId 与 permId 指回记录,追加一条状态事件(`source: "reconcile"`),重放缓冲里没对上的回报;之后这张单的回报就认得出记录 |
| ② 券商侧没有,`broker_fills` 里查得到成交 | 补录成交事件(按 exec_id 去重);数量填满的落 `filled` 终态,提醒一次 |
| ③ 其余去向不明的(包括只成交了一部分的),而且这一轮刚问过券商当天的成交 | 只追加一条 `NotAtBroker` 状态事件并提醒一次,不落终态 |

- **怎么认**:普通单的 orderRef 是记录 id。托管单的 orderRef 是 `trk:<追踪>:<单型>`,也就是它那条记录的 `signature`;同一追踪同一单型可能留下多条记录
  (被拒后重挂),再按记录状态里的 `order_id` / `perm_id` 区分,认走的单不给第二条记录。成交也按 signature 取、再按单号筛。
- **② 只认 BAG 行**:组合单 IBKR 回 1 条 BAG 行加每条腿各一行,腿加起来是份数的几倍,拿它判定填满会把只成交一半的蝶标成已成交。
- **③ 之前先问券商**:`broker_fills` 不一定是最新的,应用关着时成交的单,重启后如果直接按本地成交表下结论,就会被报成"查不到成交",照这句话重下一张就是双倍仓位。
  所以走到 ③ 之前,router 有 `executions()`(IBKR 的 reqExecutions)就先要一遍当天的成交、存进 `broker_fills`、再按 ② 结一次;
  问失败、超时或被节流时这一轮不下 ③ 的结论。券商只回当天的成交,更早成交的仍会落到 ③,提醒语写明去 TWS 核对。
  router 没有 `reqCompletedOrders`,分不出"撤了"与"更早成交了",两者都是 ③。
- **③ 不落终态**:终态在只增的库里不可逆。券商侧查不到,只能说明"这里看不见它",不能证明它被撤了;把一张还活着的单标成作废,
  比让用户多看一眼「去向不明」危险得多。
- 只成交了一部分、剩下的券商侧也没有:② 补录找到的那部分、不落终态,记录接着走到 ③,提醒语照实写
  「当天的成交里只找到 40(共 100),已补录进记录;剩下的 60 可能被撤了,也可能更早成交、券商不再回报」,
  `NotAtBroker` 事件与 `reconcile_missing` 审计里带 `filled` / `quantity`。这一句优先于下面两种提醒语:有成交就说明单子发出去过。
- 重启后没人盯的**条件单**(只在引擎内存里排队、从没发给券商的那种)也走 ③,提醒语换成"软件重启后条件单不再被盯,要继续请重新提交",同样不替用户作废。
- 发单途中被中断的记录(有 `submit_intent`、一条状态都没有,`lastStatus` 为空串)按同样三种情形处理,③ 的提醒语是
  「发单途中软件中断了,券商侧没有这张单,当天的成交里也没有它:它多半没有发出去(请在 TWS 里核对后再决定是否重下)」。

## 什么时候运行

- 接上新会话时安排下一轮(`reconcileSoon()`):断线期间的成交与撤单靠这一轮搬回来。
- 之后 60 秒一轮,挂在盯盘节拍器里,与盯盘共用追踪锁(它会改 `orderIndex` 与终态)。没有任何追踪时盯盘会提前返回,对账写在那个返回之前。
- 对账出错时留痕(`reconcile_failed`),不带垮盯盘。
- 向券商要的每样东西最多等 10 秒:底层库的这些请求没有超时,会话在请求途中被断开时结束信号永远不来,而对账持有跨引擎实例共用的追踪锁。
  未成交单列表超时,这一轮作罢(留痕 `reconcile_failed`);当天成交超时(`reconcile_fills_failed`),这一轮照常做 ① 与 ②、不下 ③ 的结论。迟到的结果丢掉。
- 当天成交最多 5 分钟问一次(reqExecutions 回的是当天全部成交),计时从发出请求算起,所以问失败之后也要等满 5 分钟;
  待定的单都已经标过 `NotAtBroker` 时不问。接上新会话、进程启动、引擎重建之后的第一次不受这两条限制。

## 刻意放过的

| 放过谁 | 原因 |
|---|---|
| 最后一次动静不到 2 分钟的单 | 券商侧的未成交单列表有滞后。最后一次动静取记录创建与最新一条状态事件里晚的那个(等了几小时才触发的条件单,一发出去就是刚发的);最新那条晚于这一轮开始时刻时,从记录创建算 |
| 本进程还在盯的条件单 | 它本来就没发给券商;队列在等券商回话之前先记一份,等待期间触发发出的不算失联 |
| 账户会话没连上的记录 | 读不到的账户(`coveredAccountIds()`)这一轮整个跳过,否则每次断线都会把它们报成去向不明;自动重连回来立刻安排一次对账 |
| 7 天前的记录 | 已经是历史,只会让对账变慢 |
| 托管单本身的认领(`hostedIndex`) | 归 `adoptHosted`,它还负责同 ref 重复单的去重(留单号最新的,其余撤掉)。对账读未成交单列表时会把每一张单登记进券商层的改单缓存 |
| 富途 | router 没有 `listOpenOrdersDetailed`,空转;富途走拉取式的 `syncBrokerOrders` |

## 界面

`NotAtBroker` 在记录页与看板上显示为黄色的「去向不明」,不混进蓝色的「进行中」;记录页的状态筛选有同名的一档。
