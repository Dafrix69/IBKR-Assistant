# 性能留痕

问"慢在哪"时要有原始记录可查,而不是靠猜。这份文档写引擎记什么、怎么从原始记录重算,以及哪些记录不是这份代码自己写的、可以拿来对照。

## 引擎记什么(`engine-ts/src/rpc/perfLog.ts`)

每个 RPC 请求记两段:**排队**(收到 → 开始执行,排在本地道 / 读道 / 交易道上等了多久)与**执行**(开始 → 答完)。

| 记录 | 什么时候写 | 内容 | 理由 |
|---|---|---|---|
| `[rpc] 慢请求 <方法> <执行毫秒> ms` | 排队或执行任一段 ≥ 1 秒 | 数字是执行时长;排队 ≥ 100 ms 时补「,排队 N ms」 | 格式不变,以前的日志与分析照读;只记执行时长分不出"自己慢"与"被前面挡住" |
| `[perf] {json}` | 每 10 分钟一行;窗口里一个请求都没有不写;引擎退出时补写一行 | 每个方法的道、次数、两段各自的 p50 / p90 / p99 / 最大;合约确认那道闸(`qualifyGate.ts`)这一窗口里超时、当场答、试探各几次 | 一天 144 行,看得出哪一段变慢又不刷屏 |

- 分位数是最近秩;每个方法每个窗口最多留 5,000 个样本,再多按蓄水池抽样,次数与最大值另记不丢。
- 只有方法名与毫秒数,不记入参;日志落盘前照常过主进程的脱敏(`redact.js`)。
- 时长用 `performance.now()`:它在 macOS 的睡眠里也走,睡眠中途答的请求会把睡着的时间算进去。要分睡眠用 `[power]` 那两行或 pmset(见下)。

## 从原始记录重算(`desktop/tools/log_report.js`)

读原始 `main.log`(可再给一份 `pmset -g log` 的输出),算出:各方法慢请求的分位数、正好等满一个超时(12 秒 ± 150 ms)的次数按天分布、
其中多少落在睡眠里;「节拍停了」一共几次、几次的停摆区间(写日志那一刻往前推停了多久)和某段睡眠重叠。journal 里引用的数字由它算,
别人拿同一份日志能算出同一个数。

## 正在运行的应用多大(`desktop/tools/perf_snapshot.js`)

在用户自己的终端里跑(沙箱不让跑 `ps`):每类进程(主进程、渲染、GPU、引擎、读窗口的程序)常驻内存与 CPU 的中位数、最小、最大,
安装包与 DMG 的大小,引擎起来到连上券商的时长。重写的基线与对比都用它,两边用同一份脚本量才比得了。

## 不是这份代码自己写的记录

结论能不能站住,要拿和这份代码无关的记录对照:

| 要证明什么 | 拿什么对照 |
|---|---|
| 某次停摆是不是电脑在睡 | `pmset -g log`(系统自己记的 Sleep / DarkWake / Wake);主进程的 `[power]` 两行是另一路(Electron `powerMonitor`) |
| TWS 到底回没回合约确认 | TWS 的 API 消息日志(TWS「全局配置 → API → 设置 → 创建 API 消息日志文件」),每条收发带时刻。里面有账号,不进仓库、不进诊断包 |
| 一笔单成交了没有、成交价 | IBKR 的结单(Flex Query / 活动报表),券商自己的账 |
| 定价函数对不对 | 标准正态分布表与 Black–Scholes 的解析解(`pricing-identities.spec.ts` 最后一组),不经过这份代码 |
| 时钟在睡眠里走不走 | `mach_absolute_time` 与 `mach_continuous_time`(一个十行的 C 程序就能读),见 journal |
