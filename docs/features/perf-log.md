# 性能留痕

问"慢在哪"时要有原始记录可查,而不是靠猜。这份文档写引擎记什么、怎么从原始记录重算,以及哪些记录不是这份代码自己写的、可以拿来对照。

## 引擎记什么(`engine-ts/src/rpc/perfLog.ts`)

每个 RPC 请求记两段:**排队**(收到 → 开始执行,排在本地道 / 读道 / 交易道上等了多久)与**执行**(开始 → 答完)。

| 记录 | 什么时候写 | 内容 | 理由 |
|---|---|---|---|
| `[rpc] 慢请求 <方法> <执行毫秒> ms` | 排队或执行任一段 ≥ 1 秒 | 数字是执行时长;排队 ≥ 100 ms 时补「,排队 N ms」 | 格式不变,以前的日志与分析照读;只记执行时长分不出"自己慢"与"被前面挡住" |
| `[perf] {json}` | 每 10 分钟一行;窗口里一个请求都没有不写;引擎退出时补写一行 | 每个方法的道、次数、两段各自的 p50 / p90 / p99 / 最大;合约确认那道闸(`qualifyGate.ts`)这一窗口里超时、当场答、试探各几次 | 一天 144 行,看得出哪一段变慢又不刷屏 |

- 分位数是最近秩;每个方法每个窗口最多留 5,000 个样本,再多按蓄水池抽样,次数与最大值另记不丢。
- 只有方法名与毫秒数,不记入参;日志落盘前照常过主进程的脱敏(`redact.js`)。
- 时长用 `performance.now()`:它在 macOS 的睡眠里也走,睡眠中途答的请求会把睡着的时间算进去。要分睡眠用 `[power]` 那两行或 pmset(见下)。

## 从原始记录重算(`desktop/tools/log_report.js`)

读原始 `main.log`(可再给一份 `pmset -g log` 的输出),算出:各方法慢请求的分位数、正好等满一个超时(12 秒 ± 150 ms)的次数按天分布、
其中多少落在睡眠里;「节拍停了」一共几次、几次的停摆区间(写日志那一刻往前推停了多久)和某段睡眠重叠。journal 里引用的数字由它算,
别人拿同一份日志能算出同一个数。

## 正在运行的应用多大(`desktop/tools/perf_snapshot.js`)

在用户自己的终端里跑(沙箱不让跑 `ps`):每类进程(主进程、渲染、GPU、引擎、读窗口的程序)常驻内存与 CPU 的中位数、最小、最大,
安装包与 DMG 的大小,引擎起来到连上券商的时长。重写的基线与对比都用它,两边用同一份脚本量才比得了。

## 不是这份代码自己写的记录

结论能不能站住,要拿和这份代码无关的记录对照:

| 要证明什么 | 拿什么对照 |
|---|---|
| 某次停摆是不是电脑在睡 | `pmset -g log`(系统自己记的 Sleep / DarkWake / Wake);主进程的 `[power]` 两行是另一路(Electron `powerMonitor`) |
| TWS 到底回没回合约确认 | TWS 的 API 消息日志(TWS「全局配置 → API → 设置 → 创建 API 消息日志文件」),每条收发带时刻。里面有账号,不进仓库、不进诊断包 |
| 一笔单成交了没有、成交价 | IBKR 的结单(Flex Query / 活动报表),券商自己的账 |
| 定价函数对不对 | 标准正态分布表与 Black–Scholes 的解析解(`pricing-identities.spec.ts` 最后一组),不经过这份代码 |
| 时钟在睡眠里走不走 | `mach_absolute_time` 与 `mach_continuous_time`(一个十行的 C 程序就能读),见 journal |

## 下单时延(`orchestrate/engine.cpp` 的 `StageClock`)

每条指令处理完,引擎写一行 `[order] 指令时延 <总> ms(本地速记 | 大模型 | 未解析):现价 a · 解析 b · 合约时段 c · 校验 d · 落库 e · 合约号 f · 中间价 g · 发单 h · 收尾 i`。
只有段名与毫秒,不记指令内容与账户。钟是 `util::awakeMicros`(不算睡眠)。各段的意思:

| 段 | 从哪到哪 |
|---|---|
| 现价 | 指令里抽出来的标的向券商取现价(常驻行情流命中时是零;夜盘指数要等期货 − 基差) |
| 解析 | 本地速记,或大模型往返 |
| 合约时段 | 期权与组合的交易时段(按天缓存)。合约号(组合的每条腿)在这一段开头同时问出去,不在这里等 |
| 校验 | 代码校验(同步) |
| 落库 | 写记录与警告事件 |
| 合约号 | 第一张真要发出去的单之前,等上面预取的合约号回来(多半在合约时段那一问期间已经回来,接近零);全被拦下的指令没有这一段 |
| 中间价 | 只有 AUTO_MID:订各腿行情、等齐买卖价 |
| 发单 | `place`:合约号(多半已在缓存)、下一个订单号、`placeOrder` 写进 socket |
| 收尾 | 发单之后的记账与通知 |

「发单」结束的那一刻,订单的字节已经交给 TWS(IBKR 认得这张单了);之后 TWS 回状态是异步的,不算在里面。
一条指令扇出到几个账户、几笔单时,「落库 / 中间价 / 发单」按笔各记一次。回包(`instruction.submit` 的结果)不带这些数,界面与夹具看到的回包不变。

结构上决定快慢的几处:

- 组合的 N 条腿的合约确认一次全发出去再等(`ib_session.cpp` 的 `qualifyLoop`),是一次到 IBKR 服务器的往返,不是 N 次;
  解析出来就开始问(`EngineRouter::warmQualify`,只问期权与组合、只在真发单时问),和合约时段那一问同时走;被拦下的单不等它。ApiNext 限速每 100 毫秒 4 条:铁蝶四条腿再加时段那一条,第五条多等 100 毫秒。
- AUTO_MID 的组合盘口先看一眼、之后 25 毫秒看一次(`BrokerRouter::legQuotesHeld`);腿上的行情订阅等 `placeOrder` 写出去之后再撤——
  撤订阅的消息排在发单前面会占掉限速名额,发单就要多等 100 毫秒。
- 夜盘的指数现价要基差,基差要两段 30 根 1 分钟 K 线:同一个基差同一时刻只算一趟,后来的(下单前的取价、行情页、情报)等同一趟;
  两段各等 30 秒(`kBasisBarsTimeoutMs`,估的、没量过),不等会话缺省的 90 秒。算不出来照旧退回昨收并在警告里写明;
  到点之后 TWS 那边的请求不撤(同原来的 90 秒)。

## 下单时延模拟(`tests/tst_order_latency.cpp`、`tests/sim_tws.h`)

真的 `TradingEngine` + `BrokerRouter` + `IbApiNextSession` + `ApiNext`,下面一个在 socket 层按时延表回话的假 TWS(真钟、真 QTimer)。
量的是从进引擎到 `placeOrder` 的字节落到 socket 的毫秒数,外加每一段。几个交易员各连下两单(当天第一次碰这个到期日 / 换了行权价):
写了价的蝶、中间价蝶、贷方价差、中间价铁蝶、股票限价、大模型(固定 2.2 秒的替身)。时延表:合约详情 250 毫秒(走代理)、
期权首笔价 350、指数首笔价 150、下一个订单号 3;`SIM_ALL=1` 再按本机直连(合约详情 80)跑一遍,`SIM_TRACE=1` 打印每一条请求的时刻,
`SIM_REPORT=<文件>` 把每一单的分段写成 JSON。这些是设定不是实测:模拟用来比"同一份设定下改之前、改之后差多少"和"哪一段占大头",
真机的数以主日志的 `[order] 指令时延` 为准。

`budgets` 按时延表卡结构:写了价的组合 < 2 次合约详情往返,中间价组合 < 1 次往返 + 首笔价 + 200 毫秒(铁蝶多 100);
`overnightSharesBasis` 卡夜盘基差共用一趟。
