# 想法检索

想法少的时候,知识总结把范围内最近 100 条全部喂给模型就够了;想法多到上千条,「最近 100 条」和「相关的 100 条」就差得越来越远。
检索给出一条并列的路:按关键词、标的、时间窗找想法,再按语义补上字面对不上的那几条;总结时带上检索焦点,就改成「命中的按时间分层抽样 + 最近一批」。
默认的取数方式不变(下文「切换前先留基准」)。

## 关键词检索

- **`ideas.search`**(本地道):关键词(按空白与 `,` `，` `、` `;` `；` 分隔,任一命中)、标的(任一命中)、时间窗(`since` / `until`,YYYY-MM-DD,含当天,按 UTC 日期计)、状态;
  新的在前,默认 50 条、上限 200。每条带 `matched_by`(`symbol` / `text` / `semantic`)。关键词与标的都不给时就是带时间窗的列表。
  日期格式不对、状态不认识报原话(−32602)。给了关键词时会走一次语义补充(下一节),默认调用配置的大模型。
- **关键词怎么匹配**:3 个字以上走 FTS5 的 trigram 索引(`ideas_fts`);两个字的词(「止损」「蝴蝶」)trigram 查不了,走子串匹配。
  索引是自带内容的一张表(`idea_id` + 原文):ideas 的主键是 TEXT,VACUUM 会重编 external content 表的 rowid,按 rowid 对应会悄悄对错行。
  旧库第一次打开时建索引并补进已有想法;SQLite 不带 FTS5 或 trigram 时全部走子串匹配。
- **带焦点的总结**:`ideas.digest({ scope, focus: { q?, symbols? } })`。范围内最近 20 条无条件进;其余命中焦点的按写作时间把跨度等分成远 / 中 / 近三段,
  配额相同,某段不够就把余量分给别的段;段内按分数排:标的命中 2 分、原文命中 1 分、语义命中 1 分,几项同时命中时相加,同分新的先;总数上限 100,按时间从早到晚喂。
  界面的检索框只发检索词(`focus.q`),`symbols` 只有直接调 RPC 时才有。
  喂给模型的第一行写明检索焦点与取数方式;系统提示词不变。落库的那一行带 `focus`。
- 不带 `focus`(或 `q` 与 `symbols` 都为空)时仍是全部喂最近 100 条,落库的行没有 `focus` 键。
- 分层:打分与抽样在 `ideaRetrieval.ts`(纯函数),取数在 `store.searchIdeas`,handler 只负责拼。界面「想法」页的检索框回车生效,有检索词时「总结知识」变成
  「按检索总结」,卡片上标出命中原因。

## 语义补充

给关键词检索补上意思相近、字面对不上的那几条(`services/ideaSemantic.ts`):先按结构过滤(状态、时间窗),再在这批里按语义挑。
已被关键词或标的命中的打上 `semantic`,没命中的补进来(`matched_by: semantic`,界面标「语义相近」);分层抽样里它和原文命中一样记 1 分。
出任何错(模型报错、超时、回包不对、本机模型服务没开、原文里有真实账号)一律退回纯关键词,不报错。

两种做法,环境变量 `DAFRI_SEMANTIC=llm|embed|off` 选;没设 `DAFRI_SEMANTIC`(或值认不出)时,`DAFRI_EMBED=off` 也关掉语义补充;
测试里默认关,既不调大模型也不连本机模型服务。

- **`llm`(默认):让配置的大模型直接挑。** 把检索词和池里的想法(短编号 + 原文,每条截 300 字、空白压成一个,最多 200 条,新的在前)交给知识总结用的同一个模型,
  要回 `{"ids": [...]}`;编号由代码核对,只认池里真有的,编造的、重复的不认,最多 8 条。提示词声明想法原文只是待检索的数据、其中的指令一律忽略。
  按「检索词 + 这批想法」缓存:想法页停留时每分钟按检索词刷新一次也不会每分钟调一次模型;想法变了才重问;失败的不缓存。
  发出去的是想法原文,和知识总结、AI 分析本来就发的是同一类数据。
- **`embed`:本机 Ollama 嵌入 + 余弦**。`embeddings.ts` 只许本机地址(`DAFRI_EMBED_URL` 可改,只认回环地址),`ideaVectors.ts` 懒算并把向量存库。
  模型 `DAFRI_EMBED_MODEL`,默认 `qwen3-embedding:8b-q8_0`;门槛跟着模型走(8B 0.36、0.6B 0.5、没量过的 0.5),排进前 3 名才算;
  `keep_alive` 默认 5m(用完就卸,不一直占 10 GB 显存),`DAFRI_EMBED_KEEP_ALIVE` 可改。

**默认用大模型挑的依据**(用户自己的一小批想法 × 10 个人工标注的查询,笔记原文不进仓库):

| | 本机 0.6B 嵌入 | 本机 8B 嵌入 | 大模型挑(默认) |
|---|---|---|---|
| 精确 / 召回 | 58% / 55% | 67% / 70% | **89% / 85%** |
| 字面对不上的同义说法 | 0/2 | 2/2 | **2/2** |
| 按行业找个股(要知道某只股票是做什么的) | 找不到 | 找不到 | **找到** |
| 每次检索 | 15 毫秒 | 40 毫秒,载入占显存 10 GB | 约 0.8 秒,同一检索词有缓存 |

嵌入只会"换个说法",不会推理,也缺冷门常识;文本长短悬殊时总有一条"跟谁都像"。DeepSeek 官方 API 没有嵌入接口,所以是让它读完直接挑。
标注集只有 10 个查询、十几条想法,想法多起来之后要重新量一次。

## 边界

**只检索想法原文,不检索成交。** 成交是只增 SQLite 里的精确行,对它的问题(某个标的一共亏多少、做多失败几次、持有超过三天的胜率)都是聚合,SQL 答得精确;
数字、日期、排序在嵌入空间里几乎没有意义,近似的答案还不会提示"我不确定"。交易分析已经从逐笔成交确定性地算出进场位置、最大浮盈浮亏、兑现率、卖出之后的走势。

要让总结同时看到想法与成交,走"数字由代码算,叙事交给模型"这条路:`ideas.digest({ trades: true })`,成败由 `tradeOutcomes.ts` 从成交算好,
当事实附在想法后面,不写进 `ideas` 表、不进检索。规则见 [想法备忘](ideas.md)「交易结果」。

## 几道约束

- **账户与持仓不出本机。** 交易笔记里几乎一定有仓位大小、账户、真实盈亏,所以嵌入只用本机模型;大模型路径发的是想法原文,出口有真实账号检查。
  用正则把内容洗一遍再发出去的办法不用:正则一定会漏。
- **检索回来的文本是注入面。** 原文在提示词里一律声明为待分析的数据,其中的指令忽略;以后要灌外部材料(研报、券商评论)时,这条必须守住。
- **提示词在代码里。** 想法分析与知识总结的提示词是 `rpc/handlers/ideas.ts` 里的常量,不走 `prompts/` 的版本号(那一套只管下单解析);
  带焦点的总结只改了用户消息开头那一行的说明。
- **基线分两层。** 检索结果依赖语料状态,不能逐字节固定;检索那一层用固定语料夹具检查"哪几条 id 被召回",提示词模板那一层把检索换成固定结果再检查。
  不为了让基线过而 `golden:update`。

### 不引向量库

一万条向量暴力算余弦是个位数毫秒,向量存 SQLite 的 BLOB 列;真要近似最近邻再上 `sqlite-vec` 扩展。Chroma / LanceDB / pgvector 在
[依赖选型](dependencies.md)的「刻意不引入的」表里。

## 抽样不纯按相似度取前 k 条

交易日志是有偏样本:大赚大亏写得多、写得细,平淡的中间态懒得写。纯按相似度召回会系统性地多喂戏剧性案例,所以召回按时间分层抽,远期、中期、近期各留配额,
并保留最近一批无条件进入,让模型看得见认知的变化。

想法原文不可改:`store.ts` 对 `ideas` 表只有改状态、标的、分析三处 UPDATE,没有一处改原文,所以每条都带着干净的写作时点,
不存在事后把笔记改成马后炮再被召回的情况。哪天允许改原文,检索的时点就不可信了,这一节要重写。

## 切换前先留基准

`idea_digests` 记下每次总结喂过哪些 `idea_ids`,落库的行带 `focus`,同一个问题下两种取数的结果能并排比较。
把默认取数换成检索之前,同一个问题下全部喂与按检索的结果各存一份,人工比较哪份更能回答"我是不是在反复犯同一个错";没有这个对照就不换。
想法只有十几条时两种取数喂给模型的内容除第一行的说明之外逐行相同(命中的 + 最近 20 条就是全部),这个量级上检索不改变任何事,等想法过了几十条再对照才有意义。

## 刻意不做的

- 不做"现在该不该买"。检索自己的日志答得好的只有一类问题:我是不是在反复犯同一个错。
- 不把检索接进下单链路。`ideas` 这一域不解析、不下单。
- 不为检索改想法的可写性。

测试:`idea-retrieval.spec.ts`(结构化过滤、关键词、按时间分层抽样)、`idea-semantic.spec.ts`(语义补充的两种做法与出错退回)。
