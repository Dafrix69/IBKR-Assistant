# 确认凭据:确认框和放行绑在一起

2026-09-28 加的。对应 2026-08 审计的 C2(`docs/reports/code-audit-report.md`):那条一直没有修。

## 原来的样子

`preload.js` 给每个敏感调用无条件带上 `__confirmed: true`,主进程只看这个标记。确认框是界面自觉去弹的:
先 `dafri.confirm(...)`,用户点了确认,再 `dafri.submit(...)`。主进程从来不知道"弹过框"和"这一次调用"之间有没有关系。

界面里只要跑进一段别人的脚本——某个依赖被投毒是最现实的一种——它直接调 `window.dafri.submit(text, true, accounts)`
就能发单,一个对话框都不会出现。CSP、沙箱、React 转义挡的是"脚本进不来",这一条挡的是"进来了以后"。

`__confirmed` 还留着,它现在只说明"调用是从这座桥上走的"。

## 现在

会发单 / 授权发单 / 打开闸门 / 放宽限额 / 换券商的调用,主进程要一张**一次性凭据**才放行。凭据只有一个来源:
主进程自己弹的原生对话框,用户点了确认那个按钮。

| 用途(`purpose`) | 哪个调用要 | 绑着什么 |
|---|---|---|
| `instruction.submit` | `instruction.submit` 且 `execute: true` | 指令原文 + 账户别名列表 |
| `tracker.close_now` | `tracker.close_now` | 追踪 id |
| `tracker.add` | `tracker.add` 且带 `auto_close` 或 `host_at_broker` | 整个入参 |
| `broker.select` | `broker.select` | 券商名 |
| `gate.auto_execute` / `gate.allow_live_trading` / `gate.allow_combo_live` | `settings.patch` 把这个闸门**从关改到开** | 无 |
| `limits.loosen` | `settings.patch` 把限额**往松了改** | 放宽了的那几项与新值 |

口径:

- **对话框最显眼的那一行由主进程按用途写**(`PURPOSES`),界面改不了。macOS 的消息框不显示 `title`,
  所以这一行放在 `message` 里——以前 macOS 上用户其实看不到「发送真实订单」这几个字。
- **发单的确认框,连内容也由主进程写**:指令原文取自绑的那一份,账户是纸面还是实盘去问引擎(`system.status`),
  不听界面的。有实盘账户时第一行写「发送真实订单(含实盘账户)」。
- **闸门与限额的确认框,全部由主进程写**:限额从多少改到多少,它对着引擎此刻的设置算。界面说"只是从 5,000 调到 6,000"不作数。
- **凭据绑的是摆给人看的那一份内容。** 确认的是一句话、发的是另一句,不放行;那张凭据还在,留给原来那句。
- **用一次作废,一分钟过期。** 一次调用要几张就得几张都在,差一张整个拒,已有的不白烧(`consumeAll`)。
- **键的先后、`undefined` 的键不影响指纹**(`canonical`):界面拼的 spec 经过 IPC 到主进程,键的顺序不保证。

不用凭据的:只解析不发单;只设提醒价位、不授权发单的追踪;关闸门、收紧限额;熔断(尤其不能挡);删追踪;
`tracker.update`(界面上它只用来暂停 / 恢复一条追踪,没有确认框——见下面「还没做的」)。

## 界面这一侧

调用之前先 `dafri.confirm({ purpose, binding, … })`,`binding` 要和接下来那一次调用的入参是同一份内容。
`bridge.ts` 的 `ConfirmPurpose` 和主进程那张表由测试对着。

设置页的保存:先过本地检查 → 要开的闸门各确认一次 → 限额有放宽的确认一次(没有放宽的主进程直接回 `true`,不弹框)→ `patchSettings`。

## 钉住它的测试

`tests/desktop-main.spec.ts` 把主进程真的跑起来走这一段:没同意条款不放行 → 同意了但没确认不放行 → 点了取消不发凭据 →
点了确认放行到引擎(回来的是引擎自己那句话)→ 同一张凭据用不了第二次 → 改一个字不放行;开闸门与放宽限额的确认框上没有一个字来自界面。

`tests/desktop-confirm-grants.spec.ts`:哪些调用要凭据、内容变了不放行、用途不通用、过期、`consumeAll`、
界面绑的与主进程算的指纹相同;以及对着源码核对的接线——核销在转给引擎之前、凭据在用户点了确认之后才发、
确认框默认按钮是「取消」、界面上每个要凭据的调用之前都带着用途去确认。

## 还没做的

- **恢复一条暂停的追踪不用确认。** `tracker.update { enabled: true }` 会让一条带自动平仓的追踪重新生效。
  要不要在这里加一个确认框是交互上的取舍(每次暂停 / 恢复都弹一次),没有替你定。
- **确认的是原文,执行的是另一次解析**(审计 C12)。凭据绑的是指令原文,不是解析出来的那张订单;
  大模型两次解析同一句话可能不一样。要根治得有一个"按已校验的那条记录发单"的引擎方法,那要动 `engine.ts` 的
  `handleInstruction`——体积预算里写着"先做真机核对,再动它"。方案见 `docs/reports/commercial-readiness-2026-09-28.md`。
- 追踪的确认框上,价位那几行还是界面写的(要现取报价、现算)。绑的是整个入参,写错了入参对不上;但文字本身主进程没有核对。
