# 睡眠被报成「引擎卡住」,TWS 卡住时只读请求各等 12 秒(2026-10-18,从 main.log 量出来的)

起因是一个问题:应用慢在哪里,换语言能不能快。拿 `~/Library/Logs/IBKR-Assistant/main.log`(2026-09-18 起,19,653 行)量了一遍:
5,425 条「慢请求」、1,130 条「节拍停了 …」(其中 1,126 条说"电脑没睡,是引擎被挂起或卡住了")。两件事都不是算得慢,是**等**,而且都有软件上的原因。

## 一、1,126 次「电脑没睡」其实都是电脑在睡

主进程的 `power-watch` 记下了每一次 `系统睡眠` 与 `系统醒来`(Electron `powerMonitor`)。把引擎的停摆行按时刻对上去:
09-30 主进程开始记以来的 1,130 次停摆里,1,126 次的停摆区间(写日志那一刻往前推停了多久)和主进程记下的某段睡眠重叠,
而且这 1,126 次全都说成了"电脑没睡"。没重叠的 4 次:3 次在 10-05 清晨(那几天主进程的睡眠记录不全,见上一篇),
1 次是 10-15 那一段 42 小时(主进程那段时间没有记录;那一次引擎自己倒判成了睡眠)。数字由 `node desktop/tools/log_report.js` 从原始日志重算。

**根因:`performance.now()` 在 macOS 上睡眠里照走。** `wakeGuard.ts` 拿"墙钟差 − 单调时钟差"当作睡着的时长,前提是单调时钟在睡眠里不走。
本机实测(同一秒内):

| 时钟 | 秒 |
|---|---|
| `mach_absolute_time`(睡眠里不走) | 497,841 |
| `mach_continuous_time`(含睡眠) | 1,340,848 |
| Homebrew Node 26.7 的 `process.hrtime` | 1,340,848 |
| 打包版用的 Electron Node 24.18(libuv 1.52.1)的 `process.hrtime` | 1,340,848 |
| `os.cpus()` 各核时间片(user + nice + sys + idle + irq)最大的那个核 | 497,743 |

libuv 在 macOS 上取的是含睡眠的那一个,所以睡多久单调时钟就走多久,睡着的时长永远算出 0,每一次都判成"卡住"。
判成卡住的后果不只是一句话说错:**醒后"先不判断、等券商连接稳住 20 秒"那一段只给睡着的用**,所以它在 macOS 上从来没生效过。
醒来那一秒 TWS 可能给的是睡前的缓存盘口,跟踪止损的峰值是落库的,一笔旧价就能把它抬上去。09-30 那一次合盖 12 小时被报成卡住,
当时记成了"这台机器上单调时钟的判法失灵",没有查下去。

**改了什么:** 节拍器每一轮交给 `WakeGuard` 的时钟换成 `awakeClockMs()`——各核时间片计数里最大的那个,睡眠里不累加,一次 8 µs。
只在 macOS 上换;Windows 与 Linux 没有在真机上量过,留着 `performance.now()`。用例在 `tests/wake-guard.spec.ts`「醒着的时钟」。

## 二、TWS 不回合约确认时,只读的取数每一次都等满 12 秒

`options.spot` 的慢请求 1,176 次,中位数正好 12,002 ms;`pa.analyze` 487 次,中位数 12,002 ms。12 秒就是 `QUALIFY_TIMEOUT_MS`。
1,004 次 12 秒的 `options.spot` 里只有 5 次在睡眠里,其余全是醒着的;按天数,10-05 有 543 次(就是
[qualify-timeout-cached-as-unknown.md](qualify-timeout-cached-as-unknown.md) 那一晚,TWS 重启之后一次确认都没回),10-12 有 461 次
(美东 05:17–11:22,开发版,其间 `连接 live 断开 / 已自动重连` 每十几分钟一次)。

持仓的常驻行情 10-05 已经改成"按会话记、隔 30 秒试一次"(`heldStreams.ts`),别的只读路径没有:
测算面板的现价两秒一次、K 线页、盘口、报价,每一次都发一个确认、等满 12 秒。界面每一路同时只发一个(`store/spot.ts` 的 `inFlight`),
所以两秒一刷的现价实际十二秒才回一次,读道(`RpcServer.READ_CONCURRENCY`,4 个并发)里一直有一个位置被它占着,TWS 被同一个确认问了上千遍。
**别的读请求有没有因此排队,那时的日志看不出**:「慢请求」记的是开始执行之后的时长,不含排队。`positions.list` 那 195 次 12 秒
全在 10-05(持仓行情那条修之前),是它自己的确认超时,不是排队。所以从这一版起排队与执行分开记(`rpc/perfLog.ts`,见下)。

**改了什么:** 新文件 `qualifyGate.ts`,把持仓行情那一条规矩推到所有只读的确认上:按会话记,一次超时之后 30 秒内,
缓存里没有的确认当场答"没回应";到了间隔只放一路去试探;回了话就清掉。下单(`qualify`)、组合腿与 AUTO_MID 定价
(`qualifyAllOrRaise`)、托管单的触发条件(`priceCondition`)不受这道闸,照样去问,问回来了读的那几路跟着恢复。
量能流原先"这一只超时、下一轮别的照问"的那一条随之变了:这一会话半分钟内都不再问(`volume-stream.spec.ts` 跟着改)。
用例在 `tests/qualify-gate.spec.ts`。

**另加的度量:** 每个请求记"在道上排了多久"与"执行了多久"(`rpc/perfLog.ts`)。「慢请求」那一行格式不变、数字仍是执行时长,
排队超过 100 ms 时补「,排队 N ms」;每十分钟一行 `[perf] {…}`,各方法的次数与两段时长的 p50 / p90 / p99 / 最大,
外加这道闸这十分钟里超时、跳过、试探了几次。下一次再有人问"慢在哪",直接读这几行,不用再猜。
这一篇里的数字可以用 `node desktop/tools/log_report.js` 从原始 `main.log` 重算一遍(可以再给一份 `pmset -g log` 对照睡眠)。

## 没有核对的

- 两处改动都只有离线测试。睡眠那一处要合一次盖:醒来后日志里应当是「其中约 … 电脑在睡眠;醒来先不判断」,
  紧跟着「醒后等了 … 恢复判断」,不再是「电脑没睡」。
- TWS 为什么那两晚一直不回合约确认,仍然不知道(见上一篇的「没有核对的」)。这次只是让它不再拖慢别的请求。
- `macro.board` 的中位数 3.9 秒、第 90 百分位上千秒:大部分(819 次里 679 次)落在睡眠里,醒着的那部分是公开行情源的等待,没有单独查。
- `book.snapshot` 每次 3.5 秒是盘口页自己的等待时限,不是超时,没有动。
