# 电脑合盖睡着之后,IV 记录的盘口全空、模型 IV 冻住(2026-09-29,实盘 TWS,打包版)

起因是 `fly-iv/2026-09-29.jsonl`:美东 13:24:11 之前每条腿都有买卖价,之后三笔(13:46:41、15:16:53、15:32:58)
10 条腿的买卖价全是空的,模型 IV 三笔逐字节相同,15:16 与 15:32 的 SPX 现价也都是 7677.24。`main.log` 里
13:24:12 有一次「连接 live 断开」、13:24:17「已自动重连」。先怀疑的是重连之后行情没恢复、盯盘的流也一样。

**根因是电脑睡着了,不是重连逻辑。** 重连之后行情不恢复的那个漏洞是真的,但这一天救不了。

## 经过

时间都是美东(`main.log` 是北京时间,减 12 小时)。睡眠与唤醒取自 `pmset -g log`。

| 美东 | 事 |
|---|---|
| 12:53:50 | 最后一笔正常的 IV 记录(此前五分钟一笔) |
| 12:58:25 | `Entering Sleep state due to 'Clamshell Sleep' … Using Batt`:用电池,合上了盖子 |
| 13:08 起 | 只有维护唤醒(DarkWake),每次 2–21 秒,约 15 分钟一次,一直到收盘以后 |
| 13:24:11 | 唤醒的第一秒记了一笔,**有**盘口 |
| 13:24:12 → 13:24:17 | 断开、5 秒后重连;这次唤醒 21 秒,13:24:33 又睡了 |
| 13:31:27 → 13:31:32 | 断开、重连;这次唤醒 5 秒 |
| 13:46:41、15:16:53、15:32:58 | 各落在一次 2 秒的唤醒里:盘口全空,只有模型 IV,三笔一模一样 |

`main.log` 里每一次断开 / 重连、每一笔 IV 记录都对得上某一次唤醒,精确到秒。同一段里「慢请求 positions.list 909906 ms」、
「调用 macro.board 超时(120s)」却在 949 秒后才报:进程在睡眠里被冻住,计时器不走。

## 结论

- 醒着的那几秒里 TWS 自己也刚醒、连不上服务器,库重订了也没有东西可给。任何重订规则都救不了睡着的机器,
  这段时间里本机盯盘等于没有。应用开着 `powerSaveBlocker('prevent-app-suspension')`,挡得住闲置睡眠,挡不住用电池时合盖。
- 13:24:11 那笔盘口多半是 TWS 睡前的缓存:订阅是醒来那一秒新订的,不到一秒之后 TWS 就发现自己断了。按"最近一笔盘口到达的时刻"
  分不出这种旧盘口,盘口里没有 TWS 那边的时间戳。
- IV 记录把 4 笔坏样本写进了 `2026-09-29.jsonl`。校准只看 IV(`flyCalibration.ts` 的 `validIv`),会把它们当真。现在循环记的那一笔
  至少要有一条腿有卖价。已经写进文件的那 4 行没有动,删不删由用户定。

## 顺着查出来的:重连之后不来盘口的流,永远不会被重订

`engine-ts/tests/fix-stale-streams.spec.ts` 第一段用**真的** IBApiNext,只把最底下的 socket 控制器换成假的:

1. 1100 → 库关掉 socket → 会话层把每条流清空(不拿断线前的价冒充现价)。
2. 5 秒后库重连:会话层先补回行情类型基线,库再按**原 reqId** 把每条行情流重订一遍。reqId 按连接算,在新连接上重用是合法的;
   基线排在重订前面。这两处都不是毛病。
3. TWS 只回一笔模型 IV:句柄读到空盘口、有 IV、`error` 为空,一小时后还是这样。
4. 常驻订阅那几处(`HeldStreams.usable`、`OptionMarkStreams` 读之前)只认 `error`,这条永远算"能用":盯盘每一轮
   「拿不到现价,本轮不判断」,跟踪止损、利润回撤永远不触发。不断线、流自己没了动静的,读到的是冻住的最后一个价
   (改之前的代码上复现:价停在 18.2,盘口早变成了 22.1)。

修法:会话层给每条流记两个时刻,最近一次请求与最近一笔盘口 tick(模型 IV 与昨收不算)。连着却超过时限没有盘口
(盘中 30 秒,盘外 / 盘前 / 盘后 2 分钟,休市不判),撤掉自己那一条重订,新请求换一个新的 reqId。持仓腿、持仓正股、测算的流都这样。

同一处还有一个老漏洞,一起修了:两个账户持有同一条腿,那条流被别处撤掉(下单定价、盘口页)之后,旧代码每一轮两个键
互相撤掉对方刚订的。改之前复现:5 轮订了 13 次,主账户那条腿每一轮都读不到价。现在一边订好了,另一边直接接上。

## 没查清的,和顺带看到的

- **反复断开**(「TWS 接受了连接又马上断开」):09-29 那两段(美东 11:04–11:42、11:45–12:08)机器是醒着的,和睡眠无关。
  库收到 1100 / 2110 时会主动关 socket;如果 TWS 对刚连上来的客户端马上又报一次 1100,就正好是"连上就断、5 秒一次"。
  这只是读库代码得来的猜测,没抓到 TWS 的原话。
- **1100 / 1101 / 1102 到不了 `onConnectivity`**。TWS 用 id −1 发这几个码,库把它们当 info 事件,不进 `errorSubject`;会话层只订了
  `errorSubject`,所以 `BrokerRouter.upstreamOkFlag` 永远是 true。它只影响一句超时提示的措辞,这次没改。库对 1101(连回来了、
  订阅丢了)什么都不做;好在它在 1100 时已经关了 socket 重连,正常走不到 1101,真走到了也有上面的时限兜底。

## 之后做的:睡醒要认得出来(2026-09-30)

应用挡不住合盖睡眠(用电池时只有 `sudo pmset -b disablesleep 1` 挡得住:要 root、对整台机器生效,做不做由用户定),能做的是认出来、说出来、醒来别急着判断:

- 引擎在盯盘节拍里认停摆(`engine/wakeGuard.ts`):相邻两轮的墙钟差超过 30 秒算停摆,墙钟差减单调时钟差占一半以上算睡着。
  这一天原样回放:12:58:24 最后一轮,之后 15 次维护唤醒各是一次停摆、全在同一段里,那几秒一轮都不判断;开盖后连续一分钟没再睡才报一次。
- 醒来先等连接稳住 20 秒(连接一变重新数,最长 2 分钟)再判断。13:24:11 那次醒了 21 秒:1 秒后断线、5 秒后重连、之后稳了 15 秒就又睡了,
  那笔可能是睡前缓存的盘口不会拿去判断。这样做的理由不只是"价旧":跟踪止损的峰值落库,一笔旧价或新旧腿拼出的净价就能把峰值抬上去,
  之后拿真价一比是一次假回撤。`wake-guard.spec.ts` 里的对照:不睡的话 50 → 60 → 57 触发平仓;睡醒那一笔 60 被挡掉,57 不触发。
- 主进程:`powerMonitor` 的睡下、醒来、换电源进 main.log;用电池又有追踪在盯时提醒一次(`desktop/power-watch.js`)。

## 要在真机上核对的

- 断线重连之后行情恢复得了的时候:日志里不该出现 `[ibkr] 行情流 … 撤掉重订`(库的重订够用,时限不该误伤)。
- TWS 断网一两分钟再恢复:持仓腿在盘中过了 30 秒还没盘口时,日志有一行「撤掉重订」,盘口回来后有一行「重订 N 次后盘口回来了」,
  追踪卡片的现价接着动。
- 盘中一只成交稀的持仓正股:看它多久被重订一次(0 次最好;每分钟一次也能接受,是一次撤订加重订)。
- 合盖睡眠醒来之后:第一分钟里追踪卡片与 IV 记录的状态;醒来那一刻的旧盘口有没有触发什么(按上面的分析,判不出来)。
- 用电池、有一条追踪在盯,合盖十几分钟再打开:main.log 里依次有 `[power] 系统睡眠,用电池`、`[盯盘] 节拍停了 …(其中约 … 电脑在睡眠…)`、
  `[power] 系统醒来,睡了 …`、`[盯盘] 醒后等了 N 秒 … 恢复判断`,开盖一分钟后 `[盯盘] 这一段停摆结束` 与一条通知;追踪卡片那 20 秒写「电脑刚醒」。
- 合盖期间的维护唤醒:每次一行 `[盯盘] 节拍停了`,不该有「恢复判断」。Electron 的 `resume` 在维护唤醒里来不来没核对过:
  数一数 `[power] 系统醒来` 的行数,对一对 `pmset -g log` 里的 DarkWake。
- 拔掉电源(有追踪在盯):一条「正在用电池」的通知;同一段电池期间不再提醒,接回电源再拔才又提醒。
